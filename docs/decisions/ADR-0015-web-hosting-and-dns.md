# ADR-0015: Web Hosting and DNS for `16ane.com`

- **Status:** Proposed (2026-10-19), and already in effect: the site went live on Cloudflare on 2026-10-19 (see *Cutover log*). The maintainer chose Cloudflare over Firebase Hosting and dropped Firebase entirely; the rest is open for review in #36.
- **Date and owners:** 2026-10-19 | 16ane Maintainers
- **Related requirements:** REQ-012 (no-value disclosures)
- **Related epics and issues:** E01, E15; #32 (public readiness), #36 (this site), `ISS-017` (`app.16ane.com`, separate)
- **Related ADRs:** `ADR-0010` (security headers baseline), `ADR-0013` (licensing, `web/.well-known/security.txt`), `ADR-0014` (brand and domain isolation)

## Context
Before this ADR, `16ane.com` served a placeholder ("16ane is paused while we build the next version.", last modified 2026-09-04). The page appeared to be served by Firebase Hosting: the apex and `www` `A` records were `199.36.158.100` and the zone carried `hosting-site=solaanedotcom`. This repository contains no site code. `ADR-0014` expects the domain to point at an Open Agent Economy overview, with the legacy marketplace retired, and `docs/protocol/DEVELOPER_INTERFACES.md` proposes nine subdomains. None of them exist.

## Options
1. **Option A: Cloudflare Workers with static assets, an assets-only Worker (no script), Worker Custom Domain on the apex, zone on Cloudflare.**
2. **Option B: Cloudflare Pages.**
3. **Option C: Stay on Firebase Hosting.**

## Evidence and sources (checked 2026-10-19)
- **Assets-only Workers are supported and free to serve.** "The `main` key is optional for assets-only Workers" ([Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/)). "Like Pages, requests for static assets on Workers are free" ([Pages to Workers migration](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/)). "Requests are only billable if a Worker script is invoked" ([static site generation](https://developers.cloudflare.com/workers/static-assets/routing/static-site-generation/)).
- **Workers vs Pages.** The docs do not plainly say "use Workers for new projects". They do present Workers as the migration target, saying "Workers has a distinctly broader set of features" (migration guide above). Choosing Workers is our judgement, not a quoted recommendation.
- **`_headers` and `_redirects` work for static assets**, but are "not applied to responses generated by your Worker code" ([headers](https://developers.cloudflare.com/workers/static-assets/headers/), [redirects](https://developers.cloudflare.com/workers/static-assets/redirects/)). With no Worker script, every response is a static asset, so they always apply.
- **`_redirects` cannot redirect by host.** "Domain-level redirects" are listed as unsupported ([redirects](https://developers.cloudflare.com/workers/static-assets/redirects/)). For `www` → apex the docs point to a Redirect Rule with a proxied placeholder record ([redirect www to root](https://developers.cloudflare.com/rules/url-forwarding/examples/redirect-www-to-root/)).
- **Custom Domains** need "an active Cloudflare zone", can be the apex, and can be declared in Wrangler config as a route with `custom_domain: true`. "You cannot create a Custom Domain on a hostname with an existing CNAME DNS record" ([custom domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)). The page does not say what an existing `A` record does, so the cutover below removes it first.
- **`not_found_handling: "404-page"`** serves "the nearest 404.html" with a 404 status ([static site generation](https://developers.cloudflare.com/workers/static-assets/routing/static-site-generation/)).
- **`workers_dev: false`** disables the `workers.dev` route on the next deploy, but "does not disable Version URLs, Preview URLs, or Deployment URLs" ([workers.dev](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/)).
- **Precedent:** [`bytesbrains/copra`](https://github.com/bytesbrains/copra) serves `copra.dev` the same way (`wrangler.jsonc` with `assets.directory: "./web"`, a strict `web/_headers`, `noindex` on preview hosts).

## Security and legal impacts
- **What the page may claim.** Only what `docs/planning/LAUNCH_READINESS.md` records: gates `G1-12` (Base Sepolia deployment) and `G1-13` (hosted faucet/demo server) are FAIL, so the page says plainly that nothing is deployed. It must carry `TEST TOKENS (tANE) - NO CASH VALUE` (REQ-012) and state that there is no token sale, presale or tradable token (`AGENTS.md`). `test/web/site.test.ts` enforces this in CI.
- **No third-party code.** The page is static HTML and CSS: no JavaScript, fonts, analytics or CDNs. The CSP is `default-src 'none'` with only `'self'` for styles and images, which is stricter than copra's.
- **Account and token risk.** Whoever controls the Cloudflare account controls `16ane.com`. The zone and the Worker live in the BytesBrains account (`admin@bytesbrains.com`, account ID `1539190079828744a96d18d3fa1b4241`), which needs 2FA. `wrangler.jsonc` pins that `account_id`, because the first deploy attempt went to a maintainer's personal account through Wrangler's default login. Workers Builds deploys from Cloudflare's GitHub integration, so no Cloudflare API token is stored in GitHub. If deploys move to GitHub Actions later, the token must be scoped to Workers deploy only, with no DNS edit.
- **Impersonation.** A "crypto" domain attracts copycat scams. The page states where official contract addresses will be published (this repository and this page), and that anyone selling 16ane tokens is not 16ane.
- **Email.** `16ane.com` is a Google Workspace alias domain of the BytesBrains Workspace, with aliases `admin`, `contact`, `hello`, `notify`, `security`, `support` and `unsubscribe`. SPF and DKIM authenticate mail Google sends for the domain, but they do not stop spoofing on their own: receivers only reject or quarantine forged `@16ane.com` mail once DMARC is enforced. DMARC starts at `p=none` (reports only), so until the rollout in *Remaining steps* reaches `quarantine`, the aliases are **not** protected from spoofing. That gap matters for a crypto-adjacent domain that tells people to trust only official channels, so the rollout has dates. SPF stays `~all`, as Google recommends ("Google recommends you use **~all**", [SPF setup](https://knowledge.workspace.google.com/admin/security/set-up-spf)); DMARC enforcement, not `-all`, is what blocks spoofed mail. An earlier draft of this ADR proposed null-MX "sends no mail" records; those would break the aliases and must not be published. `SECURITY.md` still lists GitHub private reporting only; whether to add `security@16ane.com` is a separate maintainer decision.

## Decision
Adopt **Option A**:
1. **Hosting.** An assets-only Worker named `16ane-site`, configured in root `wrangler.jsonc`, serves `web/`. Wrangler is pinned in `package.json` (`ADR-0013` pinned-lockfile rule).
2. **Domains.** `16ane.com` is a Worker Custom Domain (`routes[].custom_domain`). `www.16ane.com` is a proxied placeholder record (`AAAA 100::`) plus a Cloudflare Redirect Rule `https://www.16ane.com/*` → `https://16ane.com/${1}`, 301, preserving the query string. `workers_dev` is off. Branch previews stay on (`previews`) and are sent `X-Robots-Tag: noindex` from `web/_headers`.
3. **Deploys.** Cloudflare Workers Builds, connected to `bytesbrains/16ane` with production branch `main`. Unlike the GitHub Actions deploy proposed in #36, this keeps no Cloudflare token in GitHub, and it matches copra. CI (`.github/workflows/site.yml`) checks the page but does not deploy it. Until Workers Builds is connected, a maintainer deploys by hand with `npx wrangler deploy` using the `bytesbrains` Wrangler profile, and only from a commit on `main`.
4. **DNS records (maintainer, Cloudflare dashboard).**

   | Name | Type | Value | Proxy | Purpose |
   |---|---|---|---|---|
   | `16ane.com` | Worker | `16ane-site` (created by the custom domain) | proxied | the site |
   | `www` | `AAAA` | `100::` | proxied | target for the redirect rule |
   | `16ane.com` | `TXT` | `google-site-verification=…` | n/a | Google Workspace domain ownership |
   | `16ane.com` | `MX` | `1 smtp.google.com` | n/a | mail for the aliases goes to Google Workspace (Google's current single MX value; the legacy `aspmx` set is still supported but not needed, per [MX setup](https://knowledge.workspace.google.com/admin/domains/set-up-mx-records-for-google-workspace)) |
   | `16ane.com` | `TXT` | `v=spf1 include:_spf.google.com ~all` | n/a | only Google may send as `16ane.com` |
   | `google._domainkey` | `TXT` | DKIM key from Google Admin | n/a | signs outgoing mail |
   | `_dmarc` | `TXT` | `v=DMARC1; p=none; rua=mailto:admin@16ane.com` | n/a | reports only, so not yet enforced; see the DMARC rollout step |

   No Firebase records remain: the `A` records were deleted at cutover, and the `hosting-site` TXT record should be deleted too.
5. **Remaining steps.**
   1. Delete the `hosting-site` TXT record, and turn on *Always Use HTTPS* so `http://16ane.com` redirects (see log).
   2. **DMARC rollout**, following Google's [recommended rollout](https://knowledge.workspace.google.com/admin/security/recommended-dmarc-rollout) ("Start with a policy set to **none** ... for one week"):
      - from 2026-10-19: `p=none`; review the daily aggregate reports sent to `admin@16ane.com`;
      - from 2026-10-26, if every legitimate sender passes: `p=quarantine; pct=5`, raised in steps to `pct=100`, with at least a week at each step;
      - then `p=reject`. Record each change and its date in this ADR.
   3. ~~Confirm the first Workers Builds deploy from `main` is live~~ (done 2026-10-19, see log): `https://16ane.com/.well-known/security.txt` shows the comment from `main`. After that, never run `wrangler deploy` by hand.
   4. Make `bytesbrains/16ane` public (#32). Until then, every GitHub link on the page is a 404 for visitors; the maintainer accepted that on 2026-10-19.
   5. Enable DNSSEC in Cloudflare and add its `DS` record at Squarespace. Do this last.
   6. Delete the old Google Cloud DNS zone and the Firebase site.

## Consequences
- The site costs nothing to serve and has no runtime code to patch.
- Other subdomains (`docs.`, `app.`, `faucet.`) can be added later as separate Workers on the same zone.
- Redirect, DNS and mail records live in the Cloudflare dashboard, not in this repository. This ADR is the record of what they should be.

## Alternatives rejected
- **Option B (Pages):** It would work, but static assets on Workers serve the same files at the same price, and copra already uses Workers. Using one model for both projects is simpler.
- **Option C (Firebase):** The maintainer chose Cloudflare. It also keeps DNS, TLS, redirects and hosting with one provider.

## Open risks
- **Workers Builds and fork pull requests.** The builds page does not say whether pull requests from forks get preview builds. Check this before the repo goes public, because a fork preview would run the fork's build command. If they do, restrict builds to branches in this repository.
- **Wording drift.** The page repeats facts from `LAUNCH_READINESS.md`. When a gate changes, update the page in the same pull request.
